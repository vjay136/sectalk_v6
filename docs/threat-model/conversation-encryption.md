# Conversation encryption

Workspace owners can choose server-managed encryption for newly created workspace channels after verifying their authenticator. A channel keeps the mode assigned at creation. The server wraps each message's AES-256-GCM data key with the tenant's versioned key. The application database still records the channel, sender, message identifier, timestamps, and ciphertext length. Recipients need current scope to decrypt or search retained text through the service. An operator with the service's wrapping credentials and access to tenant key material is within the managed encryption trust boundary.

Members can explicitly share a decrypted, exact-revision snapshot with authorized Safety reviewers. That snapshot resides in the private report store. Workspace review requires additional consent and a Safety handoff. Compliance exports select exact eligible reports under a matching active legal hold and require an independent approver. The export is encrypted at rest. See [Storage lifecycle](../STORAGE_LIFECYCLE.md).

Rooms and standard workspace channels use standard workspace storage. Room creation and the selected room display that mode. Room text is available to the service under the room's scope for live mentions and threads, indexing, and authorized moderation. Applying the managed channel policy affects only newly created channels.

Secure direct messages open in a dedicated view after both accepted contacts opt in. Each approved browser publishes a signed Ed25519 and Curve25519 device identity and signed one-time prekeys, bound to the browser's existing approval key. Users compare safety numbers or scan a QR code before trusting the device set. The Matrix crypto SDK uses device-to-device Olm sessions to transfer the sending device's Megolm ratchet key. Each direct message stores one Megolm ciphertext and any accompanying Olm key envelopes for eligible devices. This protocol shares the sender ratchet over pairwise sessions and uses that ratchet for message bodies. Device changes require a new safety-number check and create a new sender namespace.

Protected groups use one Megolm sender session per sending browser and roster epoch. The approved-device group epoch key encrypts each exported sender key for that epoch. The sending browser signs the ciphertext and key capsule together. A join, removal, or device change rotates the epoch, and old messages retain their original format. Approved same-account device transfers can restore eligible encrypted group history. Anyone who saved prior ciphertext and a prior sender or epoch key may still decrypt material covered by those keys.

The service retains ciphertext and routing metadata, including account, conversation and device identifiers, event order, timestamps, payload length and key-envelope recipients. It can deny or delay delivery. An attacker who controls an approved browser or the application code loaded by that browser can access plaintext there. A locally stored verified safety number can flag later directory changes after users compare it over a trusted channel. Group search runs on approved devices. Users can choose to disclose specific group messages to Safety from the reporting workflow.
